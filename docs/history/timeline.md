## 2026-11-16

一天內做了很多決定，依先後：

1. **改走像素、維持原生 Swift**（[ADR 0005](../adr/0005-pixel-art-swiftui.md) 取代 0001）。不再做 AI 生成 3D 與 RealityKit 驗證（S1、S2），玩偶照片不必上傳第三方；紙片 2.5D 不再是備案。作者要求重新評估 Flutter，最重視互動效能，評估後仍選原生（[素材與引擎調查](../research/asset-and-engine.md)）。
2. **自己的 iPhone 用免費 Apple ID 就能裝**；Team ID 放進不進 git 的 `ios/Config/Signing.local.xcconfig`（[實機測試](../research/device-testing.md)）。
3. **遊戲設計**：寫好 [遊戲設計](../product/game-design.md)。拖曳的做法從願景原本的「拖曳引導，牠們會跟著走」改為「把牠拎起來」。路線圖重寫：A1 粗估從 2～3 週改為 4～6 週（加入捲動箱庭、找路、資料化的行為與日夜），新增「A1 之後：庭院與家具」。
4. **視角從「俯視斜角」改為等角**：俯視斜角做出來太平面，作者看過等角與「斜俯視娃娃屋」兩張色塊樣品後選等角（參考 Project Zomboid）。箱庭大小從「約 2×1.5 個畫面」改為 12×12 格。
5. **A1 第 1 項**：等角屋內箱庭（四件色塊家具、前後遮擋）。
6. **A1 第 2 項：鏡頭**。
   - 拖曳時畫面來回閃：手勢掛在會跟著鏡頭移動的背景上，用預設的 `.local` 座標量拖曳量，形成回饋。改用不會動的外框量後修好。
   - 鏡頭原本一次跳一整個箱庭像素（3pt），作者希望跟著手指走，改為對齊螢幕實體像素。
   - 臨時加入雙指捏合縮放：最大 3pt、最小房間左右塞滿，捏時連續、放開吸附到整數倍。
7. **程式地圖**與檢查它和檔案一致的測試（[程式地圖](../code-map.md)）。
8. **動作改成資料、載入時預先算好每一格**：原本每格當場合成（Mac 上量一格約 0.09 毫秒）。作者選「打開 App 就全部算好」。
9. **載入畫面與技術取捨原則**：用首次載入換遊戲中的順暢；空間換時間超過 50MB 或會隨內容成長時先討論（[架構的技術取捨](../architecture.md#技術取捨)）。
10. **繪圖從 SwiftUI 改為 Metal**（[ADR 0006](../adr/0006-metal-rendering.md)）：作者要求不以開發便利為主重新評估（[渲染效能評估](../research/rendering-performance.md)）。
    - 原本每個東西是一個 SwiftUI view，每格要比對、排版整棵 view；改成 `RoomStage`（純邏輯）＋ Metal 貼圖＋有變化才畫的遊戲迴圈。
    - 刪除 SwiftUI 版的 `PenguinView` 與轉 `CGImage` 的 `PixelImage`。
    - 換完後模擬器截圖和 SwiftUI 版逐像素相同；房間邏輯、鏡頭與縮放的數學、動作、`Behavior`、`Memory` 都沒改。
    - Xcode 26 起要另外下載 Metal Toolchain。
11. **文件整理**：現行文件只寫現況，舊紀錄集中到這個資料夾；調查文件中 3D 路線的部分封存。
12. **第一次實機測試（iPhone 11、iOS 18.7.8）**：用指令編譯、安裝、啟動（信任開發者帳號後可執行）。作者覺得認得出是牠、操作順，比例有點扁之後再調；正式版量 40 秒 0 次卡頓，第一次點企鵝主執行緒慢 39 毫秒。ADR 0005、0006 改為 accepted；A0 的實機確認完成。
13. **事件紀錄改為背景寫入**：原本每次點擊都在主執行緒同步存檔，推測是 39 毫秒的原因，改成 `ModelActor` 背景寫入（每件都存）。過程中實測發現「從主執行緒建立的 ModelActor 會在主執行緒工作」，所以一律在背景建立。之後兩次實機量測結果不一（3 次延遲、最長 238 毫秒；以及 0 次），延遲多發生在遊戲迴圈閒置後第一次畫，39 毫秒是不是資料庫造成的，還沒確定。
14. **加常駐量測點（signpost）再量**：iPhone 11 正式版 40 秒、1,069 格，一格中位 1.37 毫秒、最慢 5.84 毫秒；暫停後醒來的第一格等畫布 4 毫秒，證實方向但量級小，閒置暫停保留。這次沒有延遲，四次量測兩次重現不了，偶發的 39～238 毫秒不在我們的程式裡。作者決定先結案，量測點保留，覺得卡時再錄。
15. **分支與版本規範**：之前都直接 commit 到 main。改為從分支開發、經由 PR squash 合併，GitHub 規則集強制、沒有例外；每次合併升一版並打 tag。App 版號從 Xcode 預設的 1.0 改為 0.0.1，集中到 `Base.xcconfig`。第一個走新流程的是這次的規範本身，合併後成為 v0.0.1。
16. **A1 第 3 項：第二隻（v0.0.2）**：`RoomStage` 從一隻改為多隻，每隻有自己的位置、動作與狀態機；點擊判斷點到哪一隻，重疊時前面那隻優先；鏡頭回到兩隻的中點。第二隻先用灰色剪影，事件紀錄記成 `placeholder-2`。
17. **分成兩種分支**：原本「每次合併都升版、打 tag」，改為快速分支（一件事、進 main 不升版不打 tag）與版本分支（`release/vX.Y.Z`，一批事、進 main 時升版並打 tag）。
18. **ship skill**：commit、push、開 PR 的步驟（逐檔加入、掃描、測試與文件檢查）寫成 `.claude/skills/ship/`，作者同意這類動作時照著做；掃描寫成腳本 `scan.sh`。做的過程中發現這台 Mac 的語系下，忽略大小寫的中文正規表示式比對不到，改用固定字串。之後定下分工：PR 之前由 Claude 做，作者在 GitHub 按 Squash and merge，說「合併了」後 Claude 收尾（同步 main、清分支、版本分支打 tag）。

## 2026-11-17

- **A1「動起來」改順序**：原本是先寫找路，再畫「背面、側面與走路」的圖，接著寫閒晃；第二隻的剪影一直在畫面上。作者決定先修第一隻的比例（原本在小待辦，不影響順序），把走路的美術全部畫完，再寫找路與閒晃。寫移動的期間第二隻先藏起來，第一隻走穩後再回來，同時處理兩隻互相讓路，以及閒晃的「走去黏著另一隻」。圖的寫法改成和遊戲設計一致：斜向的左前、左後，右邊用翻轉。A1 從第 4 項起重新編號，共 21 項。
- **比例延後到 A1 最後**：量玩偶照片後發現，像素圖的身體只占全身高度 25%，照片是 43%。試過把身體往下拉長 7 格，整體寬高比從 0.91 變成 0.75，和照片一樣。作者看過選了這版，但哈囉的部件改好、角色包重新匯出後，作者覺得更不協調，就恢復原版。Q 版的大頭是刻意的，照照片比例拉長反而失衡。作者覺得扁不急，比例調整移到 A1 最後（第 20 項），斜向與走路的圖照現在的比例畫。其餘項次往前遞補。
- **第 4 項：第一隻的斜向四個方向**：左前、左後在私有素材 repo 和作者逐格調整後定稿。兩者輪廓相同（只差前後），共用一份；整隻相對腳底中心往右 2 格，左斜才有感覺。右前、右後由左邊翻轉，帽子不跟著翻、畫在頭後面。左後的尾巴原本畫成凸出輪廓的小突起，作者改成只用陰影暗示。
- **第 4 項：左前、左後的慢走**：先聊牠怎麼走再畫（走法見[遊戲設計](../product/game-design.md#平常沒人碰時)）。第一版試過把身體旋轉與縮放，邊緣多出零星像素、還少一列，改成只用整列平移。作者看過第一版後追加「手上下晃」，從四種晃法中選了跟著搖擺 1 格。左後的遠腳在定稿圖裡被身體擋住，走路時只有近的腳進出，像單腳跳；作者選了往後踩時從身體下面露出一列。
