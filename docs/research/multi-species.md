# 多種動物：名單、物種與動作（重構計劃）

2026-11-20 評估。作者說之後會加入其他動物（例如鯊魚）：互動事件大致相同，個性與互動權重不同。作者問兩件事：一家兩隻的 `familySize` 是不是太死；現在企鵝的資料結構，加鯊魚容不容易。作者要求先做深層的重構計劃，趁程式還小把長期的做法定下來。

**結果**：作者 2026-11-20 決定：
- 動作走 B：匯出成資料，App 只放播放器。
- 現在就做，第 13 項先暫停。
- 統稱用「角色」。
- 鯊魚比企鵝高、比企鵝瘦 1/3，放得進一格，所以第 5 段不做。

寫成 [ADR 0009](../adr/0009-characters-species-motion-data.md)；v0.0.9 照這個方向改完，作者同日在 iPhone 上確認正常後定案。實作時定下的細節（預設名單寫在程式裡、灰色剪影的哈囉是幾個關鍵影格）以 ADR 為準。

## 結論

- **`familySize` 確實太死。** 一家有幾隻寫在程式裡（`CharacterPackLibrary.familySize = 2`），但一家有誰、誰排第一已經是資料（`family.json`）。這個常數同時管三件事：最多載幾個角色包、補幾個空位給替身、記憶體測試算幾隻。起點也只有兩個（`GameView.startPositions`），第三隻會用 `index % 2` 拿到第一隻的起點，兩隻疊在同一格。
- **加鯊魚現在不容易，但難的地方很集中。** 模擬的節拍與事件、閒晃、找路與讓路、繪圖、事件紀錄都不分物種，幾乎不用改。真正綁死企鵝的是「動作與造型」這一串：
  - 姿勢的欄位是頭、手、腳、壓扁、搖擺。
  - 造型檢查寫死 `body`、`arm`、`head` 與兩隻腳。
  - 把姿勢換成部件矩陣的算式直接寫部件名稱。

  鯊魚沒有手腳，這一串要整串換掉。
- **建議：**
  - 統稱改成「角色」。
  - 名單改成資料，取代 `familySize`。
  - 動作改成由私有素材 repo 匯出的資料，App 只留一個不分物種的播放器。之後加一種動物或一個動作，App 都不用改程式。
  - 在第 13 項（打瞌睡與睡覺）之前做，因為第 13 項本身就要加兩個動作。

## 現在哪裡綁死企鵝

| 層 | 現況 | 加鯊魚時 |
|---|---|---|
| 名單 | `familySize = 2`；`loadFamily` 回傳剛好兩個位置，缺的補 nil；起點只有兩個 | 要改（第 2 段） |
| 名字 | `PenguinID`、`PenguinBehavior`、`PenguinMotions`、快照的 `Penguin`、繪製清單的 `.penguin` 等。型別名稱約 90 處，變數名稱另外一百多處 | 鯊魚的身分會叫 `PenguinID`，要改（第 1 段） |
| 狀態機 | 意圖（待機、站著、哈囉、走路）不分物種；走路的快慢用企鵝的步態名稱（`walk`、`trot`） | 意圖沿用；快慢改成不分物種的「慢、快」（第 1 段） |
| 閒晃 | 權重、冷卻每隻一份（`wander.json`）；活動的種類不分物種 | 沿用；走路快慢的欄位跟著狀態機改名 |
| 模擬 | 節拍、事件、上台下台、讓路都用身分；每隻佔一格、沿地板格線走 | 鯊魚和企鵝差不多大、也在地板上移動就不用改；不一樣時見第 5 段 |
| 動作 | `HelloMotion` 的欄位是舉手角度、歪頭、揮手；`Gait` 是搖擺、下沉、拍手、抬腳。姿勢 `RigPose` 只有頭、手、壓扁；`VectorWalkPose` 只有上半身、近的手、兩隻腳。每個算式在 Swift 與私有素材 repo 的 JS 各寫一次，逐格比對 | 整串要換（第 3 段） |
| 造型 | 讀檔檢查要求正面有 `body`、`arm`、`head`，斜向另外要 `farFoot`、`nearFoot`（`VectorRig.validate`）；`frontTransforms`、`obliqueTransforms` 直接用這些部件名稱 | 鯊魚的部件（例如尾巴、鰭）過不了檢查（第 3 段） |
| 畫面準備 | 替身借名單裡第一個有造型的那隻；鏡頭對準腳底上方 16 單位（企鵝的身體中央）；前後排序把每隻當作佔一格 | 替身會借到別種動物的形狀；鏡頭高度要看造型（第 4 段） |
| 繪圖 | 只認部件與矩陣（`DrawList`、`SpriteRenderer`、`VectorRasterizer`） | 只要改名 |
| 事件紀錄 | 存字串 id（欄位叫 `penguinID`） | 不用改 |
| 記憶體 | 名單上每一隻的貼圖在載入時全部畫好；兩隻約 25MB | 每多一隻約多 11～14MB（照現在兩隻估），第四隻左右會碰到 50MB 門檻（第 6 段） |

## 什麼會變、什麼不變

照作者說的方向分成三類：

- **所有動物共用（程式）**：意圖與狀態機、有哪些互動、閒晃怎麼挑、模擬、找路、讓路、鏡頭、繪圖。
- **每隻不同（資料，現在已經是）**：閒晃的權重與冷卻、動作的數字；之後的個性、點一下的反應權重。
- **每種動物不同（現在寫在程式裡，要改）**：身體有哪些部件、每個意圖看起來怎麼動、怎麼移動（步態），可能還有大小。

重構的重點，是把「每種動物不同」的部分集中到一個地方，而且最好是資料。架構已經有同方向的原則：

- 角色包把造型與個性資料化，換造型不用改程式。
- 只有一隻會做的事寫進共用的程式，由那隻的資料打開。

這次把它延伸到物種。

## 重構計劃

每一段做完，測試都要通過，畫面上看起來也要和現在一樣；每一段可以分開合併。

### 第 1 段：用詞與改名

- **統稱用「角色（Character）」**：住在箱庭裡的任何一隻，不分物種。角色包、角色聖經、`LoadedCharacter`、`CharacterPackLibrary` 已經這樣用。「企鵝」是一種物種（Species）。GLOSSARY 跟著改。
- **型別改名**：`PenguinID` → `CharacterID`、`PenguinBehavior` → `CharacterBehavior`、快照的 `Penguin` → `Character`、繪製清單的 `.penguin` → `.character`，其他同樣改。只改名，不改行為；App 與專案名稱不改。
- **移動的快慢改成不分物種**：`Pace` 的 `walk`、`trot` 改成「慢、快」，意圖 `walk` 改成 `move`。每種動物自己決定慢、快各用哪個步態，例如企鵝是慢走、小跑。`wander.json` 的 `pace` 跟著換欄位名稱，舊版本照樣讀得懂。
- **事件紀錄的欄位 `penguinID` 不改名**：
  - SwiftData 可以用 `@Attribute(originalName:)` 改名，官方列為輕量遷移，但開發者論壇有改名遷移失敗的回報（見「來源」）。
  - 這一欄存的本來就是字串 id，不分物種，不值得冒險。

### 第 2 段：名單改成資料（取代 `familySize`）

- **`family.json` 升到第 2 版**，列出每一隻與牠是什麼動物：

  ```json
  { "version": 2, "members": [ { "id": "<角色資料夾>", "species": "penguin" } ] }
  ```

  一家有幾隻、順序（第一個是第一隻）、每隻的物種都由它決定，程式裡沒有隻數。第 1 版（只有 `order`）照樣讀得懂，每隻當作企鵝。
- **名單和角色包對不上時**：
  - 名單上有、角色包沒有或壞掉：那個位置照樣上台，用替身（第 4 段）。
  - 有角色包、名單沒列：不上台，記一筆日誌。
- **沒有名單時**（例如公開 repo 乾淨 clone）：用程式裡的預設名單（兩隻企鵝的位置），依名稱把角色包填進去；乾淨 clone 時畫面和現在一樣是兩個灰色剪影。
- **起點由箱庭給**：從固定的起點依序找最近的空格，幾隻都不會疊在一起。
- **記憶體預算的測試照名單算。**

### 第 3 段：動作改成資料（物種的接縫）

這是最大的一段，也是加鯊魚真正要解決的地方。有兩種做法。

**A. 每種動物一套算式，放在同一個介面後面**

- 做法：App 裡企鵝一套、鯊魚一套，負責檢查造型、動作播多久、走多快、某一刻每個部件的矩陣。私有素材 repo 的 JS 也各一套，照現在的方式逐格比對。
- 好處：改動小，保留現在的逐格比對。
- 代價：每加一種動物、每加一個動作，App 與私有素材 repo 都要寫程式。工作量是「動作數 × 物種數 × 兩種語言」，而 A1 還要加的動作有打瞌睡、睡覺、驚醒揉眼睛、跌倒、被拎著、坐著、轉頭、嚇一跳。

**B. 動作匯出成資料，App 只有一個播放器（建議）**

做法：

- **私有素材 repo 照舊用 JS 算式設計動作**，那裡仍是作者調整、預覽的地方。匯出時，把每個動作取樣成「每個部件在每個時間點的旋轉、位移、縮放」，叫做一段片段（clip）：
  - 哈囉一段。
  - 每個畫好的斜向，慢、快各一段循環。
  - 每段附上播多久、移動時一秒走幾格、播的時候面向哪裡。
- **App 只有一個不分物種的播放器**：照「在做什麼、面向哪、第幾秒」找到片段，在取樣點之間內插出每個部件的矩陣。翻轉的方向沿用現在的做法，本來就不分物種。
- **模擬與畫面準備用同一份片段**：模擬要的是動作播多久、走多快；畫面準備要的是某一刻每個部件的矩陣。
- **造型檢查不再寫死部件名稱**，改成檢查「片段用到的部件，造型裡都有」。
- **App 會拿掉的程式**：`HelloMotion`、`Gait`、`RigPose`、`VectorWalkPose`、`frontTransforms`、`obliqueTransforms`，換成片段的讀檔、檢查與播放。

結果：

- 加一種動物：私有素材 repo 畫造型、寫牠的算式、匯出，App 不改程式。
- 加一個動作：私有素材 repo 加算式、匯出。App 只在出現新的意圖時接上狀態機，例如「打瞌睡」。
- 預覽與 App 播的是同一份算式的結果，不用 Swift、JS 各寫一次。

業界也是這樣分工：2D 骨架動畫工具 Spine 把動畫存成資料，每個動畫是一組時間軸，每條時間軸是某個骨頭的旋轉、位移或縮放的關鍵影格，App 用執行階段的函式庫讀這份資料播放。這裡不用 Spine 的編輯器，改由 JS 算式產生關鍵影格。

代價：

- **內插有一點誤差**：取樣之間是直線內插，不是算式的精確值。以每秒 60 個取樣估，哈囉的舉手與揮手最大誤差不到 0.3 度（推論，實作時量）。
- **逐格比對換位置**：現在比的是「Swift 算式＝JS 算式」。改成資料後 App 沒有算式，比的是「App 播出來的值＝匯出的取樣」；算式本身的對錯在私有素材 repo 檢查。
- **私有素材 repo 的匯出要改**：這部分要和作者一起做。
- **角色包沒帶動作資料時，App 沒有算式可以補**：那隻照樣上台，但不會動手腳，走路時只是平移。現在的做法是改用作者定案的數字。
- **跟著當下狀況變的動作沒辦法先取樣**：例如被拎著時跟著手指晃、轉頭看向任意方向。真的需要時，再加一層不分物種的即時調整，例如「某個部件額外轉幾度」。這是假設，現在沒有這種動作。
- **資料量**：哈囉約 2.8 秒，每秒 60 個取樣、3 個部件、每個 5 個數字，約 2,500 個數字；步態也是同樣的規模。一隻約幾十 KB 的 JSON（推論）。

### 第 4 段：替身與鏡頭依物種

- **替身借同物種那隻的形狀與片段**：形狀相同，片段可以直接用。同物種都沒有角色包時，用灰色剪影；灰色剪影的哈囉是程式裡寫好的幾個關鍵影格，只要看得出在打招呼。
- **鏡頭對準身體中央**：從造型的畫布高度算，不寫死 16 單位。

### 第 5 段（看鯊魚的設計，假設）：大小與移動方式

模擬現在假設每隻佔一格、在地板上沿格線走，前後排序也把每隻當作一格。

- 鯊魚和企鵝差不多大、也在地板上移動：不用改。
- 比較大（例如佔兩格長）：佔用、讓路、找路、前後排序都要支援多格。
- 用不同的方式移動（例如飄在空中、走不同的路線）：要另外設計。

這些都是假設，等作者決定鯊魚在箱庭裡的樣子。

### 第 6 段（看隻數）：貼圖記憶體

- **現況**：名單上每一隻的貼圖在載入時全部畫好放著，兩隻約 25MB（第一隻 14,087KB、第二隻 11,618KB）。
- **估算**：照這個大小，第四隻左右會碰到 50MB 門檻（推論，鯊魚的大小未知）。用量會隨隻數成長，照規則要先和作者討論。
- **可能的做法**：只準備台上那幾隻的貼圖，上台時畫、下台時釋放；或調低貼圖倍率。
- **時機**：不在這次重構裡，名單超過三隻之前再決定。

## 和之後工作的關係

- **第 13 項（打瞌睡與睡覺）**：照現在的做法，要再加兩套 Swift 與 JS 算式。第 3 段做完後，App 只要把新的意圖接上狀態機，動作本身是資料。所以建議先做第 1～4 段。
- **第 14 項（點一下的反應依權重）**：和閒晃一樣，有哪些反應寫在共用的程式，權重寫在每隻的角色包。某種動物沒有某個動作的片段時，那個反應不挑（權重當作 0）。這樣「互動事件差不多、權重不同」就不用為每種動物寫程式。
- **關係資料**：架構預定的 `duo.json`（兩隻共有的關係）只適用兩隻。多種動物時，改成「每一對」的關係，例如誰比較想黏著誰。這是假設，等角色聖經。

## 驗收

- **每一段**：測試全過；兩隻企鵝在模擬器與實機上，看起來、動起來都和現在一樣。
- **第 3、4 段**：加一個只在測試裡用的假物種（沒有手腳，部件例如身體、尾巴、鰭）。從讀角色包、上台、閒晃、哈囉，到產生繪製清單，App 不改程式就能跑完。

## 實作後量到的（2026-11-20）

- **內插的誤差**：用兩隻的角色包，在每兩個關鍵影格中間比「App 內插的」與「算式的」，部件套在畫布四個角上量最遠差多少：
  - 每秒 60 格時，哈囉最多差 0.23 度。
  - 慢走 0.004 度、0.03 單位；小跑 0.18 度、0.12 單位。
  - 例外是哈囉揮完那一刻：作者定案的時間軸本來就會從 -144.7 度直接跳回 -140 度，只照每秒 60 格取樣會把這一跳拉平（差 2.4 度）。

  所以匯出改成在誤差超過 0.1 單位的地方再加密，跳動的地方切到不到 0.3 毫秒，匯出時印出提醒。測試在關鍵影格上要和算式相同（1e-9 以內），中間不超過 0.1 單位。
- **檔案大小**：`motion.json` 一隻約 210～270KB（哈囉每個部件 224 個關鍵影格）；測試用的對照檔一隻約 0.9～1.1MB，不進 git。
- **測試**：188 個變成 196 個，全過；包括只在測試裡用的假鯊魚，從名單到繪製清單都跑得完。

## 來源

- **Spine 的 JSON 匯出格式**：動畫由時間軸組成；骨頭的時間軸有旋轉、位移、縮放的關鍵影格；執行階段的函式庫讀這份資料播放。見 [Spine: JSON export format](http://en.esotericsoftware.com/spine-json-format)、[Using Spine Runtimes](http://en.esotericsoftware.com/spine-using-runtimes/)，2026-11-20 查證。
- **SwiftData 欄位改名**：WWDC23 示範用 `@Attribute(originalName:)` 改名，屬於輕量遷移（[Model your schema with SwiftData](https://developer.apple.com/videos/play/wwdc2023/10195/)）。開發者論壇有 iOS 17 改名遷移失敗的回報，原因未確認（[Lightweight Migration Issues](https://developer.apple.com/forums/thread/734479)）。2026-11-20 查證。
