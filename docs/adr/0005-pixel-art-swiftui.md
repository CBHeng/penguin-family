# 角色走像素，畫面用 SwiftUI 與自寫的像素合成

[ADR 0001](0001-realitykit-swiftui.md) 以真 3D 為前提選了 RealityKit，並寫明素材若不走真 3D 要重新檢視。2026-11-07 起改用像素原型：第一隻的正面圖與拆部件的「哈囉」動作定案，2026-11-16 在 App 裡跑起來，放大不糊、動作和預覽逐格相同。作者 2026-11-16 依模擬器的畫面決定走像素。

## 決定

- **角色與箱庭都用像素圖。** 原始尺寸的小圖合成後整數倍放大，不做平滑處理。（2026-11-16 補充：「整數倍」以螢幕實體像素算；作者加入雙指縮放後，捏合中的倍率可以暫時不是整數，放開後吸附回整數倍。）
- **繼續用原生 Swift，不改 Flutter 或 Unity。** 走像素後，ADR 0001 選原生的主要理由（真 3D）不成立，Flutter 重新變成可行選項，作者熟悉它，開發會比較快。作者 2026-11-16 評估後仍選原生，因為最重視互動效能：這款的效能差別在「點下去到畫面與觸覺回應」，原生少了 Flutter 引擎與平台通道兩層，Flutter 在 iOS 的觸控延遲則是最近才宣稱修好；沒有證據顯示 Flutter 較好（見[評估](../research/asset-and-engine.md#像素路線重新評估-flutter查證日期2026-11-16)）。另外，部件合成、角色包、狀態機、事件紀錄與測試都已用 Swift 做好，觸覺與主畫面小工具也是原生較順。作者的 iPhone 11 是 60Hz、支援 Core Haptics，120Hz 不是考量。
- **畫面用 SwiftUI，部件合成自己寫。**（2026-11-16：「畫面用 SwiftUI」由 [ADR 0006](0006-metal-rendering.md) 取代，箱庭改用 Metal 畫；部件合成自己寫的決定不變。） 合成必須在原始像素尺寸完成，才能和私有素材 repo 的預覽一致（原因見[架構](../architecture.md)）。箱庭的規模（要不要捲動、同時幾個角色、鏡頭怎麼移動）在遊戲設計時決定；到時若 SwiftUI 不夠用，可以只把顯示層換成 SpriteKit，合成仍用自己的。

## 影響

- **不做 AI 生成 3D（S1）。** 玩偶照片不必上傳到 Meshy 等第三方服務，「市售玩偶照片能否上傳」不再需要決定。
- **不做 RealityKit 驗證（S2）。** 改成驗證像素箱庭能否做出抱抱：鏡頭拉近用整數倍放大，加上 Core Haptics 觸覺回饋，以實機手感為準。
- **願景的「2.5D 箱庭」改指像素呈現。** 視角（側面橫向或俯視斜角）在遊戲設計時決定，它會決定要不要畫側面圖與背面圖。
- **紙片 2.5D 不再是備案。**

## 定案

2026-11-16 作者在 iPhone 11 實機上看過，認得出是自己的玩偶，改為 accepted。比例看起來有點扁，之後在私有素材 repo 調整像素圖；目前先聚焦遊戲與技術基底。
