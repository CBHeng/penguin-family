# 狀態與繪圖分成模擬、畫面準備、繪圖三層，模擬有自己的執行緒

## 背景

A1 第 12 項之後，台上有兩隻。之後還會有更多角色、隨機事件、日夜、AI 回覆、不在時補算，每隻的狀態機各自非同步地變化（[issue #9](https://github.com/CBHeng/penguin-family/issues/9)）。現在（v0.0.7）這些都在每個螢幕更新的同一格裡做（見[調查](../research/simulation-architecture.md#現在每一格發生什麼v007)）：

- **狀態機在畫圖的同一條路上**：遊戲迴圈每一格先推進舞台，回報「播完」「走到」，`GameView` 處理狀態機轉換與閒晃的下一步，全部做完才畫。狀態機跑多久，這一格就晚多久畫。
- **render 讀的是裝著狀態的物件**：`SpriteRenderer` 直接讀 `RoomStage`，而 `RoomStage` 同時存著意圖、走路、讓路，也負責鏡頭、前後排序、點擊判斷。
- **狀態機放在 SwiftUI 裡**：狀態機與閒晃放在 `GameView` 的 `@State`。新意圖要經過 SwiftUI 才回到舞台；意圖的編號（`serial`）是為了 SwiftUI 合併更新才加的。

作者 2026-11-20 的要求：

- 趁程式還小定下長期的做法，不拿目前量到的數字當延後的理由。
- **兩隻企鵝的狀態機不能參與 render**：資料上，render 不讀、不呼叫狀態機；時間上，狀態機跑多久都不會讓任何一格晚畫。
- 模擬用固定節拍每秒 30 次，畫面內插。

## 決定

### 三層，值只往一個方向傳

```
輸入（手勢、AI 回覆、計時器……）→ 事件佇列
  → 模擬（自己的執行緒，每秒 30 個節拍）→ 快照、輸出事件
  → 畫面準備（主執行緒，每次螢幕更新）→ 繪製清單
  → 繪圖（Metal）
```

| 層 | 做什麼 | 不做什麼 |
|---|---|---|
| 模擬 | 持有唯一的世界狀態。每個節拍處理事件，推進每隻的狀態機、閒晃、走路、讓路與兩隻之間的協調，交出快照與輸出事件 | 不碰畫面、不讀系統時鐘、不知道螢幕更新率、不在主執行緒 |
| 畫面準備 | 用最近兩個快照內插，算姿勢、鏡頭（含拖曳、捏合、閒置後回去）、前後順序，交出繪製清單。點擊判斷用最近一次的繪製清單，產生「被點」事件 | 不改世界狀態、不做遊戲判斷、不等模擬 |
| 繪圖 | 照繪製清單把貼圖與多邊形交給 GPU | 不算姿勢、不排序、不讀模擬 |

### 模擬

- **固定節拍每秒 30 次**，數字可以調。模擬的時間就是節拍數，不讀系統時鐘。驅動它的地方照真實時間決定要跑幾個節拍；每次有上限，避免卡住之後越追越慢。
- **會改變世界的都是事件**：主人點擊、AI 回覆、計時器、步數都排進佇列，在節拍開頭依序處理。
- **結果固定**：亂數放在世界狀態裡。同樣的起始狀態加上同樣的事件，一定得到同樣的結果。執行緒只在驅動的地方，不影響模擬的結果。
- **重的工作**（找路、AI）在模擬的執行緒上跑，不會拖到畫面。之後如果會拖慢節拍，可以再改成送出請求、結果當成事件回來。
- **輸出事件**交給外面：事件紀錄（Memory），之後還有觸覺（Feel）、台詞（Soul）、對話泡泡（SwiftUI）。

### 執行緒

```
模擬的執行緒                              主執行緒
等到下一個節拍，或有事件進來                CADisplayLink（螢幕節奏）
取出事件 → 跑節拍                         讀最新兩份快照 → 畫面準備 → 有變化才畫
發布快照 → 叫醒畫面                       手勢 → 點擊判斷（用繪製清單）→ 事件送進模擬
輸出事件 → 轉回主執行緒                    收輸出事件 → 事件紀錄、SwiftUI
```

- **世界狀態只有模擬的執行緒能碰。**
- **跨執行緒只傳值**：進去的是事件，出來的是快照與輸出事件。交接處用 `Mutex`（iOS 18 起，見[調查](../research/simulation-architecture.md#swift-的工具)）。
- **模擬的程式不放在 MainActor**：專案預設是 MainActor，所以模擬的型別要標 `nonisolated`（`PenguinBehavior` 已經是）。
- **模擬落後時不等它**：畫面停在最新的快照，照常準備、照常畫，不會掉格；看起來只是企鵝慢了一下。
- **沒事時兩邊都休眠**：模擬睡到下一個排定的時間（例如站滿）或有事件進來；畫面照 [ADR 0006](0006-metal-rendering.md) 暫停，模擬發布有變化的快照時再叫醒。
- 模擬的執行緒怎麼計時（專用的 `Thread`、dispatch 計時器或 actor），重構時比較後再選，選擇與理由記在架構文件。

### 快照與繪製清單

- **快照**：每個節拍一份，不能修改的值（`Sendable`），保留最近兩份給內插。內容是每隻在哪、面向哪、在做什麼、這個動作從第幾個節拍開始，不放畫面的東西。
- **繪製清單**：畫面準備的結果。每一項都可以直接畫：用哪張貼圖或哪段多邊形、在畫面上的四個角。

### 狀態分三種存

| 狀態 | 例子 | 放哪裡 |
|---|---|---|
| 世界狀態 | 每隻在哪、狀態機、閒晃、走路、誰在等誰 | 模擬（一個值型別，只在模擬的執行緒）。不放 SwiftUI 的 `@State` |
| 呈現狀態 | 鏡頭、縮放、進行中的手勢 | 畫面準備（主執行緒）。丟掉也能從快照重新算出來 |
| 長期紀錄 | 發生過的事 | 事件紀錄（已經有）。要不要定期存世界狀態、重開 App 時接回去，這份不決定 |

### 遊戲迴圈（和 ADR 0006 的關係）

畫面這一側照 [ADR 0006](0006-metal-rendering.md)：跟著螢幕節奏醒來、有變化才畫、沒東西在動就暫停。改變的是：

- 推進世界的工作從遊戲迴圈移到模擬的執行緒。
- 遊戲迴圈每一格只做畫面準備與繪圖。

定案後，0006 的「遊戲迴圈」一條要加註指向這份（改 0006 要先問作者）。

## 為什麼

- **狀態機在資料上、時間上都不參與 render**：作者 2026-11-20 的要求。模擬在自己的執行緒，跑多久都不會讓任何一格晚畫。
- **邏輯成本和螢幕更新率脫鉤**：120Hz 的手機也只跑每秒 30 個節拍（[Godot：Using physics interpolation](https://docs.godotengine.org/en/stable/tutorials/physics/interpolation/using_physics_interpolation.html)）。
- **結果每次相同**：bug 可以用同樣的事件重播；測試用節拍數，不用假時間（[Gaffer：Fix Your Timestep!](https://gafferongames.com/post/fix_your_timestep/)）。
- **非同步的來源依序進入**：多隻狀態機與 AI 回覆不會同時改同一份資料（[Game Programming Patterns：Event Queue](https://gameprogrammingpatterns.com/event-queue.html)）。
- **模擬與繪圖各有自己的資料**：和 Unreal 讓繪圖跑在自己執行緒上的做法相同，兩邊不共用會變動的資料（[Unreal：Threaded Rendering](https://dev.epicgames.com/documentation/en-us/unreal-engine/threaded-rendering-in-unreal-engine)）。
- **render 只畫**：繪圖層簡單，以後換繪圖技術時只要換這一層。

## 考慮過的其他做法

- **三層都在主執行緒**：資料上已經分開，同步最少。但狀態機跑的時間仍和畫圖共用主執行緒，不符合「時間上不參與」，作者 2026-11-20 不選。
- **變動時間步**（現在的推進方式）：不用內插、沒有延遲。但邏輯成本跟著螢幕更新率走，結果也會隨每一格的時間點有些微不同。
- **每秒 60 個節拍**：延遲是 30 個節拍的一半，邏輯成本加倍。作者選 30，數字可以調。
- **render 自己內插、算姿勢**：少一層，但 render 會混進繪圖以外的運算。
- **ECS 存狀態**：實體很多時最有利。我們只有幾隻角色加一些物品，抽象成本大於好處（見[調查](../research/simulation-architecture.md#狀態怎麼組織)）。

## 代價

- **重構**：`RoomStage`（約 680 行）與它的測試要拆成模擬與畫面準備兩部分；`GameView` 只剩外殼。
- **跨執行緒**：
  - 事件與快照的交接要用 `Mutex` 保護。
  - 輸出事件要轉回主執行緒。
  - 模擬要有自己的計時與休眠，並和畫面的暫停配合。
  - 執行緒的問題比較難重現，所以交接的程式要盡量少，邏輯都留在模擬裡（模擬本身可以不靠執行緒單獨測試）。
- **延遲**：畫面落後模擬一個節拍，主人的點擊也要等下一個節拍才處理。每秒 30 個節拍時，點下去到看到反應，比現在多約 33～67 毫秒。手感以實機為準；不夠的話可以把節拍數調高，或在畫面準備先給立即的回饋（例如觸覺）。
- **畫面準備仍然每一格在主執行緒跑**（內插、姿勢、排序），但不含狀態機與遊戲邏輯。
- **新名詞**：節拍、快照、事件佇列、繪製清單、模擬的執行緒，寫在架構文件裡（GLOSSARY 只收領域用語）。

## 影響（定案後）

- **程式**：
  - `PenguinBehavior`、`WanderRoutine`：沿用，改由模擬持有，在模擬的執行緒上跑。
  - `RoomStage`：拆成模擬（走路、讓路、站滿）與畫面準備（鏡頭、縮放、排序、點擊判斷）。
  - `GameView`：不再持有狀態機；`serial` 可能可以拿掉。
  - `GameLoop`：只做畫面準備與繪圖，有變化才畫。
  - `SpriteRenderer`：改吃繪製清單，不再讀舞台。
  - 事件紀錄：改由模擬的輸出事件寫入（轉回主執行緒或直接交給背景的 `EventLog`）。
- **測試**：
  - `RoomStageTests` 拆成模擬（用節拍數，不開執行緒）與畫面準備兩部分。
  - 另外加「同樣的事件重播，得到同樣的結果」。
  - 加交接的測試：快照不會讀到一半、事件不會遺漏。
- **文件**：
  - 架構與程式地圖。
  - 時間線：2026-11-19 的「遊戲邏輯先不搬出 `GameView`」改由這份取代。
  - 0006 加註、ADR 索引。
  - issue #9 指向這份後關閉。
- **順序**：作者 2026-11-20 選了先寫調查與這份草稿，定案後再重構，排在第 13 項（打瞌睡與睡覺）之前。
