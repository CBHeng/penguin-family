# 角色不分物種：名單、物種與動作都是資料，App 只放播放器

## 背景

作者 2026-11-20 說，之後會加入企鵝以外的動物，例如鯊魚：互動事件大致相同，個性與互動權重不同。作者想知道兩件事：一家兩隻的 `familySize` 是不是太死，以及照現在的資料結構，加鯊魚容不容易。作者要求趁程式還小，先做深層的重構計劃（[調查](../research/multi-species.md)）。

照現在的程式（v0.0.8）：

- **一家有幾隻寫在程式裡**：`CharacterPackLibrary.familySize = 2`，起點也只有兩個；一家有誰、誰排第一已經寫在資料（`family.json`）。
- **模擬、閒晃、找路、讓路、繪圖、事件紀錄都不分物種**：都用身分認是哪一隻，繪圖只認部件與矩陣。
- **動作與造型整串照企鵝的身體寫**：
  - 姿勢的欄位只有頭、手、腳、壓扁、搖擺。
  - 造型檢查要求 `body`、`arm`、`head` 與兩隻腳。
  - 每個動作在 Swift 與私有素材 repo 的 JS 各寫一次算式，逐格比對。

  加一種動物要整串再寫一套；加一個動作，每種動物、兩種語言都要寫。

作者的決定（2026-11-20）：

- 動作改成匯出的資料，App 只放播放器。
- 現在就做，第 13 項（打瞌睡與睡覺）先暫停。
- 統稱用「角色」。
- 鯊魚比企鵝高、比企鵝瘦 1/3。

## 決定

### 用詞：角色與物種

住在箱庭裡的任何一隻都叫**角色**（Character），不分物種；企鵝、鯊魚是**物種**（Species）。程式的型別跟著改：`CharacterID`、`CharacterBehavior`、快照的 `Character`、繪製清單的 `.character`。

移動的快慢改成不分物種的「慢、快」（`Pace.slow`、`.fast`），意圖 `walk` 改成 `move`。每種動物的慢、快各是什麼步態由牠的動作資料決定，企鵝是慢走、小跑。

### 名單是資料

- **`family.json` 第 2 版**：`{ "version": 2, "members": [{ "id": "<角色資料夾>", "species": "penguin" }] }`。名單決定一家有幾隻、順序（第一個是第一隻）、每隻的物種，程式裡沒有隻數。
- **第 1 版**（只有 `order`）照樣讀得懂，每隻當作企鵝。
- **名單上有、角色包沒有或壞掉**：那個位置照樣上台，用替身，身分用名單上的 id。
- **角色包有、名單沒列**：不上台。
- **沒有名單或名單壞掉**（例如公開 repo 乾淨 clone）：用程式裡的預設名單。預設名單是兩隻企鵝的位置，依名稱把角色包填進去，填不滿的位置是灰色剪影。
- **起點由箱庭給**：從箱庭的起點依序找最近的空格。

### 動作是資料，App 只有一個播放器

- **動作的算式只在私有素材 repo**。作者在那裡設計、預覽；匯出時取樣成片段（clip），寫進角色包的 `motion.json` 第 2 版。
- **片段的內容**：每個部件一條軌道，軌道是一串關鍵影格 `[時間, 旋轉, 橫向縮放, 縱向縮放, 位移 x, 位移 y]`。旋轉與縮放以部件的轉軸為中心，再加上位移；沒有軌道的部件在原位。
- **哪些動作**：一次性的動作（例如哈囉）有長度、播的時候轉向哪裡，以及每個畫好的方向一段片段。步態分慢、快，各有一秒走幾格、一個循環多長，以及每個畫好的斜向一段循環片段。
- **App 的播放器不分物種**：照「在做什麼、面向哪、第幾秒」找到片段，在關鍵影格之間內插（旋轉照角度內插）。翻轉的方向照造型的翻轉資料，和現在一樣。
- **模擬與畫面準備用同一份**：模擬讀動作的長度、播的時候轉向哪裡、慢與快一秒走幾格；畫面準備讀某一刻每個部件的位置。角色沒有某個動作時，那個意圖馬上算播完。
- **造型檢查不寫死部件名稱**：讀角色包時檢查片段用到的方向與部件，造型裡都有；對不上時，這隻的動作資料不用。
- **匯出取樣每秒 60 個關鍵影格，誤差太大的地方再加密**：匯出時檢查每兩格中間，App 內插的和算式差超過 0.1 單位（部件套在畫布四個角上，約 3 倍螢幕的一個實體像素）就從中間再切一格。算式本身跳動的地方會切到不到 0.3 毫秒，匯出時印出提醒。

### 替身與鏡頭依物種

- **替身借同物種那隻的形狀與動作**：形狀相同，片段直接用。同物種都沒有角色包時，用灰色剪影；它的哈囉是程式裡寫好的幾個關鍵影格，只要看得出在打招呼。
- **角色包沒帶動作資料，或資料對不上造型時**：那隻照樣上台，用預設的走路速度。牠不會動手腳，走路時只是平移。
- **鏡頭對準身體中央**：從造型正面的畫布高度算，不寫死企鵝的高度。

### 不改的

- **模擬的佔用、讓路、找路與前後排序**：仍是每隻佔一格。鯊魚比企鵝瘦，放得進一格。
- **事件紀錄存的欄位名稱 `penguinID`**：SwiftData 改名有遷移失敗的回報（見調查的來源）。這欄存的本來就是字串 id，不分物種；Swift 端的參數改叫 `characterID`。

## 代價

- **關鍵影格之間是直線內插**，不是算式的精確值。2026-11-20 用兩隻的角色包量，每秒 60 個關鍵影格時，哈囉中間最多差 0.23 度，小跑 0.18 度、0.12 單位。哈囉揮完那一刻，作者定案的時間軸本來就會從 -144.7 度直接跳回 -140 度。只照每秒 60 格取樣的話，這一跳會被拉平成 1/60 秒的轉動（差 2.4 度），所以匯出時才在誤差大的地方加密，畫面和 v0.0.8 一樣。
- **逐格比對換位置**：App 沒有算式，比的是「App 在關鍵影格的時間播出的矩陣＝JS 算式的矩陣」（1e-9 以內），以及「關鍵影格之間的誤差在容許範圍內」。算式本身的對錯在私有素材 repo 預覽確認。
- **角色包沒帶動作資料時，App 沒有預設算式可以補**：現在的做法是用作者定案的數字，改成只會平移。匯出程式一定會寫動作資料，所以只在角色包不完整時發生。
- **跟著當下狀況變的動作不能先取樣**：例如被拎著時跟著手指晃。真的需要時，再加一層不分物種的即時調整。這是假設，現在沒有這種動作。
- **檔案變大**：`motion.json` 從十幾個數字變成一隻約 210～270KB 的 JSON（2026-11-20 實際匯出，哈囉每個部件 224 個關鍵影格）。讀檔在載入畫面期間做。測試用的對照檔一隻約 0.9～1.1MB，不進 git。
- **私有素材 repo 的匯出要改**，兩個 repo 要一起改、一起重新匯出。
- **貼圖記憶體會隨隻數成長**：兩隻約 25MB，照這個大小第四隻左右會碰到 50MB 門檻。這次不處理，名單超過三隻之前再和作者討論。

## 定案

提案時的條件：

- 測試全過，包括一個只在測試裡用的假物種：沒有手腳，部件例如身體、尾巴、鰭。從讀角色包、上台、閒晃、哈囉到產生繪製清單，App 不改程式就能跑完。
- 作者在 iPhone 上確認：兩隻企鵝的哈囉、慢走、小跑看起來和 v0.0.8 一樣。

2026-11-20 重構完成（v0.0.9），196 個測試全過，含假鯊魚從名單跑到繪製清單。作者在 iPhone 上確認正常。改為 accepted。
